An entity is a tenant-scoped data definition — not just a list of columns. Saving one immediately
drives every surface below, which is why an under-specified definition produces a poor application
and a well-specified one produces a usable system on the first turn.

**What a saved entity gives the tenant**

- **Entries.** Admins create, view and delete records of the entity under
  `Modules / <entity>`; editing entries isn't available yet. Each attribute becomes a stored field on the entry.
- **Forms.** `attributes` render the entry form. `html_type` picks the input control,
  `description` becomes the field's help text on generated forms and on Create Entry, and `display_label` overrides the visible label.
- **Sections.** `attribute_groups` render as the headed sections of that form, in array order, each
  with its own icon and colour. Attributes carry `group` matching a group's `key`. Ungrouped
  attributes fall outside the sections, so partial grouping looks broken.
- **Validation.** `rules` become real server-side rules on every submission, and are compiled
  into the entity's contract. They are the only thing standing between the tenant and bad data.
- **Audience scoping.** `access.visible_to` decides which of the admin, member and public surfaces
  render an attribute; `access.rules_apply_to` decides where its rules are enforced. This is how
  internal-only fields (cost, internal notes, review status) stay off member and public pages.
- **List views.** Choice attributes become filter dropdowns and rendered column labels on the admin
  list, which only works when the attribute carries its option list.
- **Pages.** Form Pages are generated from the definition, so the definition's grouping and ordering
  is literally the page layout. New assistant-generated forms are launched automatically for only
  the Admin audience, including forms generated by the `generate_page` tool. An existing form for the
  same entity version is reused with its current launch state and audiences.
- **Relationships.** An `associations` entry creates a bridge entity and both participant references
  automatically. Data that belongs to the *link* rather than to either side (a grade, a quantity, a
  joined-on date) lives in that association's `bridge_attributes`.
- **Derived values.** `kind: calculated` evaluates a `formula` over sibling slugs; `kind: computed`
  aggregates a related entity across its bridge via `aggregate`. Both are stored read-only.
- **Defaults.** `settings.default_values` pre-fills new entries, keyed by attribute `slug`.
- **Extension.** `extends` bases the entity on an existing platform model instead of a blank
  definition, inheriting its columns. A domain's person entity extends the person base model only
  when its people sign in to see their own records; that can't be undone.
- **Flowcharts.** Every form page is bound to one flowchart that processes its submissions: it
  validates, saves the record and runs any side effects. New pages use the shared "Save page record" flowchart.
- **Versioning.** Every save writes a new version of the definition, so changes are recoverable and
  an update never destroys earlier work.

Entity creation is quota-guarded per tenant, so prefer one well-modelled entity plus the supporting
entities the process genuinely needs — never a scatter of near-duplicates.

New entities and their association bridges are active immediately; there is no separate entity
launch step. Report form creation only when generation and launch succeed. Website marketing pages
use a separate draft/publication workflow.
