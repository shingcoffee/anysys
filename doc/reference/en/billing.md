## Summary

Billing is a first-class platform capability, not a `FeatureModules` registration. Catalog/policy management is under `/:cid/admin/maintenance/platform/billing/` (platform owner only); tenant subscription, invoice and method management is under `/:cid/admin/settings/billing/` (admin/owner, URL tenant scoped). Authentication and tenant guards remain controller responsibilities; see [authentication](authentication). Reads, deletion of existing resources, security settings and payment recovery remain available when creation quotas are exceeded.

Global catalog rows are Plans, PlanLimits, Coupons, CountableItems and Settings. Tenant-owned rows are Subscriptions, PlanChanges, CouponRedemptions, Invoices, InvoiceLineItems, PaymentMethods, CollectionAttempts, InvoiceSequences and Notices. Orders, charges, credentials and recurring mandates belong to platform customer **81721200**; see [payments](payments). A tenant billing ID never authorizes direct access to a platform Payments record.

## Flow

```text
Catalog command / Onboarding / tenant subscription request
    -> persisted request + purchased/target snapshot
    -> GenerateInvoice (one permanent identity)
    -> commit intent
    -> FinalizeInvoiceJob -> FinalizeInvoice -> CollectInvoice (B)
    -> MarkInvoicePaid transaction: subscription -> invoice
    -> ApplyInvoiceSettlement (A) -> committed entitlement projection
```

The daily renewal coordinator prepares the next period without advancing service. Provider attempts, reconciliation, dunning, authorization and notice dispatch belong to the invoice/collection partition. Zero invoices use the same settlement hook. A manual invoice is unpaid until owner settlement; it never authorizes a paid initial enrollment or upgrade by itself.

## Implementation

### Subscription intent and snapshots

`Subscribe.call(customer:, plan:, coupon: nil, request_key:)` returns a `Billing::Result`: `active`, `trialing`, `awaiting_payment`, `unchanged`, `conflict` or `invalid`. Only USD/CNY are supported. Currency is resolved once at acceptance (`zh` → CNY; otherwise USD). Snapshots include `plan_id`, `code`, `name`, `amount_cents`, `currency`, `interval`, `limits`, and grace policy. Catalog edits do not rewrite purchased limits/prices. Missing keys in an older snapshot grant zero capacity.

One live row includes `pending`, `trialing`, `active`, `past_due`, and `paused`. Initial positive-price nontrial enrollment starts pending and uses free fallback until paid. Its accepted period dates do not move at settlement. Ordinary request expiry uses immutable due-date grace; zero-grace initial/renewal requests remain payable through their accepted period end without unpaid purchased access. A delayed zero-total cycle settles through the ordinary hook without requiring timestamp equality or moving its accepted dates. Late positive captures after request expiry are reviewed, not reenrolled. A paid-plan trial sets `customers.trial_used_at`; cancellation/reenrollment cannot grant another trial. A free-onboarding → paid change does not grant a trial.

Request UUIDs are permanent across historical rows. Replaying a cancelled enrollment never creates a live subscription or a charge. An explicit new enrollment request can expire a logically overdue prior row even when cron is late; it retains the old debt and history. `Onboarding.call(customer)` uses a deterministic permanent enrollment UUID, checks the existing valid free default, restores `Current`, and is invoked after customer creation commits. It never seeds on GET. `StandardPlans.seed!` is an explicit command: it creates missing offerings, preserves catalog edits/archives, and seeds free limits page=10/entity=5/member=1.

### Logical current subscription and reenrollment

`Entitlements.current_subscription(customer:, at: Time.current)` is the shared read-only current-intent query. `Subscription.live` remains the stored-status uniqueness/worker scope; it does not establish reenrollment eligibility. `PlanChangePolicy.expiration_at(subscription:, at:)` uses actual trial/period boundaries, scheduled cancellation and accepted invoice request lifetime. A valid pending or paused intent remains current even though it uses free entitlements. An ordinarily renewable overdue base within grace is retained. A zero-grace renewal can prepare after a delayed scheduler, anchored to its original boundary, while the next accepted period remains current; dates advance only in settlement.

Tenant show/update/preview use the logical query. Ended requests are supplied separately as latest history, so the existing enrollment form is available without showing a current plan or future schedule. GET does not end rows, settle invoices or seed configuration. A preview against a logically ended request returns `no_active_subscription`; writes revalidate under customer → subscription → invoice locks. Explicitly voided unpaid initial invoices are ended intents, with the void row's update time as the terminal boundary.

Setup, provider discovery and default readiness use the same selector: a logically ended stored-live row cannot pin a new authorization's currency/cadence. With no current intent, setup uses initial currency resolution and monthly cadence. Existing invoice recovery explicitly uses that invoice's own subscription and frozen currency/cadence, rather than the latest enrollment's terms.

Before expiration, the domain projects already-recorded gateway/manual/zero settlements through B's `MarkInvoicePaid`; verified on-time renewal captures can advance the existing base instead of terminating it. It performs no provider HTTP. Genuine debt and immutable invoice terms remain. B's safe void conflict is honored for changes: uncertain invoices/attempts remain available for reconciliation while expired targets become terminal. Fresh enrollment is blocked with `conflict/collection_in_flight` while any historical tenant attempt remains prepared/submitting/pending/SCA/unknown or has unprojected capture evidence. Real late captures on ended requests are paid review records, not resurrection; only then can a fresh request proceed. Historical UUID replay is still unchanged.

Before a default catalog is configured, pure `StandardPlans.starter_limits` supplies deterministic finite Starter fallback: **50 pages, 25 entities, 5 members**. No read seeds a plan, subscription, settings or countable row. A configured valid free default overrides these values, including intentionally finite zero limits. An explicitly invalid default still reports `fallback_configuration_invalid`; existing subscription recovery remains available. Initial enrollment can use Starter fallback when no catalog default exists, so fresh signup and core-resource creation are not frozen.

### Plan changes, cancellation and renewal

`ChangePlan.call(subscription:, new_plan:, request_key:)` persists one outstanding PlanChange. Same target/key reuses its invoice; another target conflicts until explicit cancellation. Matching-cadence, strictly higher current-currency prices produce `awaiting_payment` proration. Lower/equal prices, cadence changes and trial changes are scheduled at the original boundary. Same plan is unchanged. Past-due, paused and pending subscriptions reject new changes; scheduled cancellation must be resumed first. Proration uses Rational time fractions and integer minor units, without floating-point money or proration coupons.

`CancelPlanChange.call(subscription:, plan_change:)` safely voids the linked unpaid invoice through B; ambiguous/captured attempts return conflict. A scheduled target already frozen into an unpaid renewal can be cancelled only through that same safe void path. Replacing that voided renewal uses a boundary-derived `:revision:<voided count>` suffix, never an execution-date key or rewritten invoice.

`CancelSubscription.call(subscription:, immediately: false)` cancels safe outstanding changes and preserves access to the current boundary. Immediate owner cancellation ends access and retains genuine debt/history. `ResumeSubscription.call(subscription:)` clears a scheduled cancellation before the boundary; it never reactivates paused/ended subscriptions or reinstates cancelled changes.

`Renewal.prepare(subscription:, at: Time.current)` returns `invoice_ready`, `not_due`, `blocked` or `ended`. It selects the scheduled target snapshot or existing purchased terms, prepares/reuses one next-period invoice, and leaves subscription dates unchanged. `ApplyInvoiceSettlement.call(invoice:, paid_at:)` runs inside B's paid-invoice transaction, applies the target/period once and records `entitlements_applied_at`. It returns `applied`, `recovered`, `unchanged` or `review_required`. Monthly/yearly arithmetic retains the original day (31st → February last day → March 31st); accepted cadence changes reset the anchor at the boundary.

An immediate change without an unresolved payment expires and is safely voided at the boundary, then renewal uses the old plan. An in-flight change blocks conflicting renewal through its snapshotted boundary grace. Valid settlement applies the target and renews from the original boundary, without retroactively moving service dates. Grace expiry ends access; late captures on ended/stale intents are review events, never silent entitlement resurrection.

### Debt and finite entitlements

`RecordInvoiceDebt.call(invoice:, at:)` marks renewal debt only, retaining `past_due_at` from immutable due_at. Proration debt never makes an otherwise paid base subscription past due. `ExpireOverdueSubscription.call(subscription:, at:)` ends pending/renewal requests at their fixed deadline and preserves unresolved capture evidence. Successful valid renewal settlement clears resolved debt; ended subscriptions require explicit reenrollment.

`Entitlements.for(customer:, at: Time.current)` is read-only and exposes `source`, `plan_snapshot`, `expires_at`, `limits` and an optional configuration `reason`. Purchased/trial limits end at their boundary, then bounded access grace uses immutable invoice/subscription policy even if cron is late. Pending initial, paused, cancelled, expired and past-access-grace customers use finite free fallback. With no configured default they receive Starter capacity; an intentional zero default remains zero. Accepted purchased limits remain immutable when the catalog changes; a missing key in a purchased snapshot remains conservative zero. Customer 81721200 alone keeps the platform quota bypass; an owner on another tenant URL does not transfer it.

Only page/entity/member quotas are published. Their authoritative counters are total-period counters; catalog commands reject relabeling them as monthly. Member usage counts member-role accounts, excluding admins. Admin user creation invokes that guard only for member accounts. The countable-items page lists every catalog row, and its On switch enables or disables any of them. Core guards remain finite when those rows are absent or disabled. Storage, support, communication, and payment rows can be toggled, but they are not enforced quotas and their usage stays nil. Quota keeps `limit`, `usage`, `remaining`, `allow?`; no data is deleted when limits shrink or fallback applies.

### Coupons and catalog commands

`ApplyCoupon.call(subscription:, coupon:)` reserves inventory atomically and creates one CouponRedemption with accepted terms. Same-code attachment is idempotent; replacement is rejected. Expiry/archive/inventory restrictions gate new redemption, not accepted discounts. Duration is relative to redemption: a positive pre-discount initial/renewal recurring subtotal consumes one eligible cycle at finalization. Free and proration invoices consume none; a 100% discounted cycle does consume one. Repeated finalization/retry cannot consume again. Void never replenishes inventory/cycles.

`Discounts.reserve_for_invoice!(invoice:)` runs in B's draft finalization transaction, returning redemption/cycle IDs, integer discount and a localized description key/values. Percent/fixed discounts are clamped to nonnegative recurring subtotal; fixed coupons require explicit USD/CNY. Tax applies after discount. Issued financial lines/terms/number/dates are immutable; policy changes affect new invoices only.

Catalog mutation uses `Catalog::SavePlan`, `SaveCoupon`, `ArchivePlan`, `ArchiveCoupon`, `UpdateCountableItems`. Save commands return `saved`/`invalid`, the record, submitted Reform `form`, and field errors. Plan limits save atomically with validated plan attributes. A catalog plan with no limit row is unlimited: the create form stores a blank value, `-1`, or `unlimited` as that sentinel. A valid free default must be active, unarchived, zero-priced in both currencies, no trial and finite for every core item. Default swaps clear the old flag in the same transaction; a database unique index prevents two defaults. The current default cannot be archived/deactivated without replacement. Referenced plan code/price/cadence identity cannot be rewritten; new priced offerings use new records. Archive retains all subscription/change/coupon history and FKs restrict hard deletion.

### Persistence, collection boundary and deployment

The consolidated `20261011000100_add_billing_subscription_lifecycle.rb` supplies all A/B billing columns/tables. Unique indexes constrain live enrollment, request identities, outstanding changes, in-flight attempts, invoice keys, coupon cycles, defaults and invoice sequences. Restrictive FKs protect financial history. `managed_by = billing` is the mandate collection-owner authority; `metadata` carries provider correlation only. Billing mandates have `next_charge_at = NULL`; ordinary Payments cron and activation/claim guards must enforce that ownership. Platform billing tokens have nil user_id and explicit purchasing-customer/authorizer fields; ordinary member tokens retain user ownership.

`Result.transaction` acquires a SQLite write reservation before state reads, with bounded busy retry outside caller-owned transactions. Lock order is subscription → invoice → auxiliary records. No provider HTTP occurs in the intent transaction. B owns immutable issue/finalization, durable invoice sequence allocation, attempt outcomes, one `MarkInvoicePaid` entry point and transactional notice/outbox creation. A calls the frozen interfaces and does not perform provider operations.

:::attention
Run the read-only `billing:repair_report` before authorizing deployment. It reports conflicting history rather than deleting it: orphans, duplicates, mismatched tenants/mandates, unfinished charges, unprojected captures, invalid defaults/amounts and unknown coupon cycles. Migration refuses detected unresolved conflicts. Reconstructed historical snapshots are marked; invoice lines/numbers remain unchanged and sequence heads use the maximum valid existing suffix. Historical authorization accounts are not inferred from today's mode.

Preflight refuses four unresolved legacy evidence classes **before the first DDL or data write**: `unpaid_active_initial_intents` identifies positive-price active subscriptions without any paid recurring-base invoice; the separate `unpaid_active_current_periods` identifies positive-price active subscriptions whose full stored current period lacks settled recurring coverage, even when an earlier cycle was paid; `unresolved_proration_intents` identifies draft/open/uncollectible prorations without a corresponding permanent target; `invoice_payment_mismatch` identifies contradictory explicit payment/order links. The report includes subscription/invoice/payment/order IDs and machine-readable payment mismatch reasons. It never infers settlement from today's catalog, treats a draft's default zero as paid, guesses a target, or swaps in another payment.

Already-paid manual invoices may legitimately have no PSP FK. Paid zero-total recurring cycles also count as settled base evidence. An unissued zero-total draft is not evidence of payment: a positive active parent is refused, while an existing pending initial parent can retain its accepted draft for ordinary finalization without gaining an entitlement receipt. When a PSP FK is present, even on a manual paid invoice, its platform payment/order ownership, exact `billing-inv-<invoice_id>` correlation, order currency, and both amounts must agree. Amounts are compared as exact BigDecimal major-units × 100 against stored invoice minor units, without rounding, FX, unit guessing or money mutation. Legacy target/access reconciliation remains an explicit evidence-based deployment step; no claim is made that these shapes exist in a live customer database.

Current-period coverage must belong to the same subscription, tenant and currency: one paid recurring interval may contain the whole current period, including a shorter target period, or an exactly adjoining paid recurring chain may cover it. Partial overlaps with no authoritative legacy intent fail closed; paid proration alone cannot establish a recurring base. The old schema identifies recurring evidence by excluding proration lines; when explicit invoice `purpose` exists, only `initial`/`renewal` qualifies. A settled proration alongside a fully paid base remains valid. Free active subscriptions and historical pending/trialing/past_due/paused/cancelled/expired states retain their dates, state and debt.

The implementation entry point is `AddBillingSubscriptionLifecycle.report(connection)`: its `paid_recurring` / `covered` recursive SQL computes this full-window evidence, and the private `ongoing_original_trial_sql(connection)` supplies the same trial predicate to both active-price checks. `AddBillingSubscriptionLifecycle#up` calls the report before adding any column; `billing:repair_report` calls that same class method and exits nonzero when findings exist. This migration/report guard is separate from `PaymentHistoricalBindingsV1` account-binding repair and does not add a runtime compatibility path.

Both active-price checks exempt only a genuinely ongoing original trial: `started_at == current_period_start`, `current_period_end == trial_end`, and `current_period_start <= now < trial_end`. Retaining `trial_end` after renewal, a future trial marker on an advanced period, or an expired/not-yet-started original active trial does not bypass settlement checks. Paid coverage after a historical trial remains valid, and the original trial dates/usage marker are preserved.

Repair report procedure:

1. Run `RAILS_ENV=production bin/rails billing:repair_report` against the intended deployment database. It is read-only, has no apply mode, and exits nonzero if any finding remains. Save the report and review each subscription ID alongside its stored dates, purchased amount, trial dates, and same-tenant/currency invoice dates/status/lines and explicit payment links.
2. For `unpaid_active_current_periods`, prove the **entire** current window. A September 1–October 1 paid invoice cannot authorize an advanced October 1–November 1 active window whose renewal is still open, even after its October due-date grace has expired. Within grace, an unpaid advanced window still is not a settled purchased period. Ambiguous overlapping promotions in the no-intent old schema require authoritative reconciliation.
3. Reconcile original settlement/access intent with owner-reviewed authoritative evidence before deployment, retaining debt and financial history. The report/migration does not pay an invoice, guess a provider/account/target, roll back dates, or change status. Rerun the report until all findings are resolved, then run the migration; `up` repeats the same preflight before mutation.
:::

### Issuance, attempts and collection policy

`GenerateInvoice.call(subscription:, purpose:, idempotency_key:, period_start:, period_end:, terms_snapshot:, plan_change: nil, extra_line_items: [])` reuses one invoice identity without replacing frozen lines. `FinalizeInvoice.call(invoice:)` issues a draft once, reserves discount/tax and allocates a durable per-customer sequence (`INV-<customer>-<at-least-five-digit-suffix>`), rather than counting drafts. Repeated issue/settlement does not renumber or recompute financial terms.

`Result.collect_after_commit` only enqueues `FinalizeInvoiceJob`; it never runs collector HTTP in a callback. The job refuses a real open transaction and invokes collection after local finalization has committed. `Cron::FinalizeDraftInvoices` recovers accepted persisted drafts before daily renewal, including pending initial and mid-period proration invoices that are not due subscription renewals. `PlanChangePolicy.accepted_invoice?` checks tenant/currency/source-period/target state. UUID or same-target replay re-enqueues the same accepted draft; repeated workers preserve one invoice, number, coupon cycle and collection identity. Database drafts are the recovery authority if the post-commit enqueue is lost.

`PlanChangePolicy.grace_deadline` governs unpaid access; `request_deadline` governs intent expiry and settlement eligibility. `Invoice#collection_deadline` delegates directly to `request_deadline`, so admission, replay and settlement use one request lifetime. Zero-grace initial/renewal requests remain payable until immutable `period_end`; a successful capture seconds after acceptance can apply the remaining purchased period without granting unpaid access beforehand. Proration retains its normal boundary hold. Overdue job disposition expires the old request and cannot create a new payment or enrollment.

Financial status (`draft/open/paid/void/uncollectible`) is separate from collection state (`ready/manual/blocked/pending/requires_action/retry_wait/exhausted/settled/stopped`). `CollectInvoice.call(invoice:, trigger: :initial, at:)` accepts initial/retry/recovery/reconcile and returns succeeded/pending/requires_action/pending_manual/retry_scheduled/exhausted/skipped/blocked. `Collector` prepares a unique CollectionAttempt plus platform payment with the same request key, commits before HTTP, then persists outcome separately. Unknown/processing/SCA keep the original identity; reconciliation projects already-captured payments and queries pinned accounts. Generic query errors do not establish nonexistence. Stripe replay without a known intent is bounded to 23 hours and the invoice deadline.

An `ApiError` is not itself a decline: collection uses `Payments::Activities::AttemptSafety.definitive_rejection?`. An uncertain/unclassified error keeps the original payment/key and unknown attempt without incrementing failures or scheduling a fresh charge. Authoritative declines release the attempt for scheduled or explicit recovery. Manual/zero transitions may run within a caller transaction because they perform no provider HTTP; positive gateway collection and provider reconciliation retain the after-commit guard.

`ReconcileCollections` also recovers accepted committed drafts if finalization dispatch was lost: pending initial invoices matching their accepted dates, next-boundary renewal invoices, and awaiting-payment proration invoices matching their outstanding change. It uses A's shared `accepted_invoice?` predicate and excludes ended/expired/stale intents. Under subscription → invoice locking, only the winning draft transition queues the existing `FinalizeInvoiceJob` after finalization commits; rollback queues nothing and repeated scans do not schedule another disposition job. Zero invoices settle locally without that collection enqueue. The same job owns expiry/initial collection; it does not enqueue itself while finalizing. The daily initial-collection population and duplicate job deliveries still pass the collector's single-attempt/payment guards, so either execution order produces one capture. A stale claim never authorizes a new charge.

Only definitive failed submissions increment `attempt_count`. Retry offsets are absolute from `first_failed_at`: `[1,3,7]` normally gives initial plus three retries, then exhaustion; a late worker skips elapsed offsets instead of bursting catch-up charges. `[]` means no retries. Missing/incompatible methods block without fake attempts; manual invoices submit no provider charge. Issued policy is immutable; `AuthorizeInvoiceCollection.call(invoice:, actor:, mode:, note:)` records an owner-only override for outstanding collection without rewriting financial terms. Dunning and initial collection select disjoint populations, while reconciliation precedes expiry decisions.

Fresh capture preparation and submission check invoice customer/currency against its own subscription and accepted snapshot. Currency mismatch returns blocked/currency_mismatch before PSP submission, not only at settlement. Historical in-flight operations remain queryable so real money is recorded/reviewed. Known account label/mode drift blocks replay/new collection, and a negative query under that drift cannot retire the original attempt as definitively absent.

`Billing::Settings` no longer selects a global `gateway_provider`; collection uses each tenant's verified default method. Settings validate tax 0..10000 basis points, nonnegative grace/notice days and strictly increasing unique positive retry offsets. Invalid raw schedule tokens remain visible on 422 rather than coercing to zero or restoring defaults; an explicit empty schedule remains empty.

`MarkInvoicePaid.call(invoice:, payment: nil, source:, paid_at:, actor: nil, reference: nil, note: nil)` is the settlement entry point. Gateway evidence must match platform order/invoice, amount/currency, recorded attempt/account/key and capture time. Manual settlement requires owner plus nonblank reference and refuses unresolved captures. Zero settlement needs no provider. Open/uncollectible debt may settle; void/ended/stale/duplicate captures remain recorded review events without automatically restoring service. Subscription then invoice locking contains the paid transition and A's idempotent projection.

### Provider authorization, removal and notices

`AvailableProviders.call(customer:, currency:, interval: nil)` returns descriptors only for implemented Stripe/Alipay adapters and eligible configured current-mode platform accounts. Setup/default readiness and provider discovery use `Entitlements.current_subscription`; invoice readiness supplies frozen invoice currency/interval explicitly. PayPal/WeChat registration does not provide Billing setup. Stripe uses deterministic Customer/SetupIntent keys and an exact platform token. Alipay supports **CNY monthly only** with signed page authorization/server query; annual setup or incompatible cadence/ceiling/calendar-anchor frequency requires reauthorization. Seed offers are monthly; owner-created annual plans require compatible authorization. Billing Alipay operations select sandbox/production by the pinned account.

`SetUpPaymentMethod.call(customer:, actor:, provider:, return_url:, request_key:)` persists tenant method/platform mandate correlation before external work. Pending setup preserves the old default. `PaymentAuthorization.confirm!(payment_method:, verified_event: nil)` consumes typed signed-account evidence or performs a server query; browser PSP IDs/return query never activate a method. Removed/expired methods cannot be revived by late success. `RemovePaymentMethod` commits removed/default=false, locally cancels its billing-owned mandate/token and records pending remote revocation; `RevokePaymentMethods` retries cleanup. Default selection is an explicit readiness-checked command.

Accepted mandate metadata includes `billing_authorization_context` with account/provider/merchant/mode. Stripe verified-event identity uses that accepted context; charge readiness rejects later account drift and historical authorization-review rows. `PaymentAuthorization.action_for(payment_method:, return_url:)` retrieves an existing correlated Stripe intent/customer or signs an Alipay handoff only: GET never creates/replays setup, saves references/tokens or activates. An incompatible completed setup does not replace the prior ready default. Unbound historical methods remain locally removable, with no guessed current-account cleanup.

Stripe identity compares the exact account row and accepted original metadata, not today's mutable merchant routing label. Setup retries retain accepted metadata parameters. Historical lookup admits the pinned account row after label/mode edits, while new setup/capture keeps drift guards. Billing Alipay historical query/refund/close/revocation selects the recorded mode when available. Correlation metadata is not another lifecycle state; absent historical credential versions and old-label external routing remain documented [Payments](payments) limitations.

`Notifier` records unique Notice business-event intents transactionally; `DispatchNotices`/`DispatchNoticeJob` dispatch after commit and recover pending work. Paid/issued notices key by invoice, failures by attempt, trial notices by trial-end, with purchasing-customer locale. `CollectionMaintenanceJob` reconciles, revokes and dispatches every 15 minutes. Notice deduplication is not an exactly-once email transport promise; see [Background jobs](background-jobs) and [Payments](payments).

## Where to pay attention

### Route audit: server authority and end-to-end invariants

Both billing surfaces are admin-category. Tenant records scope to the URL customer even for an owner; every platform action/format requires pinned owner and actual outer CID `81721200`. Browser writes accept catalog codes and stable UUIDs; prices/currency/tenant/account/tokens/return URLs remain server-authoritative. Result statuses drive truthful 303 success, 422 invalid and 409 conflict responses. Failed forms retain actual Reform form, raw limits/retry schedule and submitted coupon/provenance fields. Catalog DELETE archives; countable-item GET never seeds.

Implemented tenant additions under `/:cid/admin/settings/billing`:

| Verb/path | Contract |
| --- | --- |
| GET `subscription/plan_change_preview?plan_code=...` | Read-only kind/effective_at/currency/subtotal_cents/tax_cents/total_cents/allowed/reason; accepted commands recompute |
| DELETE `subscription/plan_change` | Cancel the live subscription's outstanding change; in-flight conflict is 409 |
| POST `payment_methods/setup_intent` | Fixed Stripe provider plus stable request UUID; returns scoped Billing ID/action/confirmation URL and top-level client_secret |
| GET `payment_methods/:id/authorization` | Scoped action/status only; provider return correlation is not activation |
| POST `payment_methods/:id/confirmation` | Exact scoped method; server-query verified confirmation |
| POST `invoices/:invoice_id/payment` | Scoped recovery trigger; tenant cannot override collection mode |

Histories/catalogs use fixed 25-row Pagy, deterministic ordering, escaped literal q and allowlisted status/tenant_id filters; pagination preserves locale/scope. The live subscription's stored currency governs display. Only authorized tenant invoice detail resolves `InvoicePaymentAction.for(invoice:)` for the exact Stripe SCA attempt; actions are private/no-store/no-referrer and absent from tables/download/owner detail. Download remains printable HTML/save-as-PDF, not a generated PDF attachment. See [Tenancy and roles](tenancy-and-roles).

Tenant presentation lives in `Customer*` subclasses that the shared components delegate to when `customer_settings: true`: `CustomerSubscriptionComponent`, `CustomerPaymentMethodsComponent`, `CustomerInvoiceTableComponent` and `CustomerInvoiceDetailComponent`. Platform views keep the base templates. The three tenant pages (`subscription`, `payment_methods`, `invoices`) render inside `Billing::Admin::CustomerBillingPageComponent.new(customer_id:, active:)`, which supplies the page header and a shared tab bar (`Plan` / `Payment methods` / `Invoices`, `aria-current="page"` on the active tab); `active:` must be `:plan`, `:payment_methods` or `:invoices`. Decorative icons come from `Billing::Admin::IconComponent`.

* **Plan** — a current-subscription card (plan name, status badges, price, renewal date, period, default payment method — the view passes the active default `@payment_method` as `default_payment_method:` — and Change plan / Manage payment methods / View invoices shortcuts) sits beside the page/entity/member usage card; unlimited meters show the count without a bar. Without a subscription the card invites the customer to browse plans. Plan cards (`li[data-plan-code]`) mark the current plan, show the monthly equivalent for yearly plans and open the `#plan-review` panel. Coupon and cancellation/resume cards sit in a bottom grid.
* **Payment methods** — saved methods render as cards (`li[data-payment-method-id]`) with provider, Default/status badges, account, authorization date and charge readiness; Remove / Continue authorization / Make Default sit in the card footer. The provider authorization section (`#authorize-payment-method`) is always visible and the header's "Add payment method" links to it.
* **Invoices** — `CustomerInvoiceSummaryComponent` shows outstanding balance per currency (linking to `status=open`), the last payment and the next renewal or scheduled cancellation above the invoice history. The controller builds the summary with `billing_invoice_summary(Billing::Invoice.for_current_customer, subscription:)`. The history embeds `HistoryFiltersComponent` with `compact: true`, a one-row toolbar with visually hidden labels; unpaid rows are highlighted and their View action is primary.

Methods, plans and coupons pass `pagination:`/`page_path:` through their mounting views and components to `Admin::PaginationComponent`; older pages are reachable through the UI. `Billing::ControllerPresentation` is a thin request adapter: controllers keep authenticated, tenant-scoped lookups and determine whether owner actions are available, then delegate billing calculations to the read-only `Billing::PresentationFacts` query API:

* `usage(customer:)`, `coupon_benefit(subscription:, pending_change: nil)` and `subscription_actions(subscription:, pending_change:, at:)` project authoritative quota counters, accepted redemption terms/remaining cycles and cancellation eligibility.
* `subscription_recovery(subscription:, invoices:, entitlements:, actions:)`, `provider_options(customer:, currency:)` and `method_readiness(payment_method:, currency:, provider_options:)` supply recovery links/access grace and provider/default readiness.
* `invoice_summary(invoices:, subscription:)` takes an already tenant-scoped invoice relation and returns `outstanding` (open/uncollectible totals grouped by currency), `unpaid_count`, `last_paid` and `renewal` (only for `active`/`trialing` subscriptions; `ends:` is true when cancellation is scheduled).
* `invoice_collection(invoice:, owner_actions: false, at:)` supplies financial/collection state, effective mode, next attempt, reasons and `can_retry`, `can_mark_paid`, `can_void`, `can_authorize_collection`. Callers authorize the invoice before querying; `owner_actions` is a controller-selected capability, never a browser field. `can_cancel_immediately?(subscription:)` supplies platform subscription eligibility.

These queries never mutate records, finalize/settle invoices, reserve discounts or call a provider. Invoice request lifetime delegates to `Invoice#collection_deadline` → `PlanChangePolicy.request_deadline`; recovery access grace remains `PlanChangePolicy.access_deadline`. Zero-grace initial/renewal requests remain recoverable through their accepted period end. Uncollectible financial status does not hide an in-flight/SCA/reconciliation collection state, and permits explicit ready-method recovery within that request lifetime. Invalid/contradictory issued policy renders unavailable rather than borrowing current settings. Projections contain no credentials; method readiness uses `charge_ready`, `ready`, `default_eligible`, `reason`/`reason_key`, and provider descriptors use `enabled`/currency compatibility. A paginated subset never establishes that every saved method is unready. Commands revalidate authoritative state under locks.

Plan preview GET serves the subscription review screen for HTML and the frozen preview fields for JSON. Failed changes retain the selected review, submitted UUID and Reform form. An accepted draft awaiting asynchronous finalization redirects with 303 and an awaiting-payment notice; an applied notice requires the command's `applied` Result. Setup/confirmation URLs use the server-generated scoped request origin and Billing method identity, never client return URLs or PSP-token hints. Platform paths with an outer CID other than `81721200` return 404 even to an authenticated owner; wrong-role requests to the canonical platform path remain authorization denials.
