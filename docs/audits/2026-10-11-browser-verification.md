### Proven isolated SQLite repair

The first final daemon, PID `14911`, used the default development WAL setting. After `bootstrap apply` and an ordinary per-record website create/read/cleanup runner cycle, its browser-database WAL and SHM descriptors were marked `(deleted)`. A second probe reproduced the condition and failed explicitly with `Deleted SQLite descriptor reproduced`; the application still returned HTTP 200 at that moment. This reproduces the historical sidecar defect on a new database rather than attributing old logs to the new suite.

Only that owned daemon was gracefully stopped. No SQLite file or sidecar was manually removed. A temporary, exact-path-guarded preload then selected a separate Rails database configuration through the supported `Rails.application.config.paths["config/database"]` setting:

```ruby
# /tmp/opencode/browser-final-sqlite.rb, loaded before application initializers
Rails.application.config.paths["config/database"] = ["/tmp/opencode/browser-final-database.yml"]
```

```yaml
# /tmp/opencode/browser-final-database.yml
development:
  adapter: sqlite3
  database: <%= ENV.fetch("E2E_DATABASE_PATH") %>
  max_connections: <%= ENV.fetch("RAILS_MAX_THREADS", 5) %>
  timeout: <%= ENV.fetch("SQLITE_TIMEOUT", 5000) %>
  pragmas:
    journal_mode: delete
    synchronous: normal
```

The preload requires the exact `browser_audit_final.sqlite3` file and matching URL, development mode, a nonsymlink database, and no assistant stub. `RUBYOPT` propagates it to the normal server and every separately launched Rails subprocess. Repository database configuration is not changed. A fresh checked connection reported `journal=delete`, then **four** normal fixture create/read/cleanup cycles all passed with HTTP 200, clean foreign-key checks, and no deleted SQLite descriptors.
